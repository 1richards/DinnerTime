<objective>
Make POST /recipes/search fast AND backward-compatible. The 28,942ms cost is a single Gemini call generating 3 COMPLETE recipes (heavy `ingredients[]` + `steps[]`). This plan adds a LIGHTWEIGHT generation path (D1) gated behind a `light` request flag so the currently-shipped app (which expects full recipes) keeps working when the server deploys ahead of the EAS build. It also parallelizes the 4 serial pre-call DB fetches (D2) and adds discovery sub-stage timing (D8-server).

Purpose: The light schema is the core ~29s→3-5s win; the `light` flag is the deploy-safety mechanism.
Output: A `light` mode on discoverRecipes + /search, parallel DB fetches, Gemini-vs-total timing in the request log.

CRITICAL BACKWARD-COMPAT: The server deploys to Fly BEFORE the EAS build ships. The OLD app calls /search expecting full ingredients+steps. If /search returned light-only, the old app would render previews with empty steps AND its save would 400. Mitigation (LOCKED in this plan): light mode is OPT-IN via `body.light === true`. Default (no flag) stays the full-recipe contract byte-for-byte. The NEW app (Plan 29-03) sends `light:true`; the old app sends nothing and gets full recipes.
</objective>
